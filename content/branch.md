## ひとことで

本線に影響を与えずに作業するための、履歴の枝分かれです。

## なぜ大事?

公開中のWebサイトを直接いじりながら改造するのは、営業中の店の厨房を工事するようなものです。途中の壊れた状態がお客さんに見えてしまいます。

ブランチは、この問題を解決します。本線（main）はそのまま公開し続け、改造は別の枝で進めます。完成して動作を確かめてから、本線に合流させる。この順番なら、公開中のものが壊れている時間がゼロになります。

AIかけこみ寺の共同開発ルールでも、複数人が同じリポジトリを別のパソコンから触る前提で運用しています。小さな修正は本線に直接入れることもありますが、大きめの改造や実験は枝を分けて進めるのが安全です。

## やさしい解説

ブランチは、レポートの下書きコピーだと思ってください。

提出用の本文はそのままにして、「試しに構成を変えてみる用」のコピーを作ります。気に入ればその内容を本文に反映し、気に入らなければコピーを捨てるだけ。本文は最後まで安全です。しかもGitのコピーは、ファイルを丸ごと複製するのではありません。

Pro Gitの解説によれば、Gitのブランチは「あるコミットを指す軽量で移動可能なポインタ」にすぎません。実体は41バイトほどのファイル1つです。だから作るのも捨てるのも一瞬で、Gitでは気軽に何本でも作るのが普通の使い方になっています。ここが、ブランチ作成が重かった昔のツールとの決定的なちがいで、Gitの最大の武器だと言われる理由です。

基本の操作はこうです。

```bash
git branch                 # いまあるブランチを一覧する
git switch -c add-wiki     # add-wikiという枝を作って移動する
（ここで編集してコミット）
git switch main            # 本線に戻る
git merge add-wiki         # 枝の成果を本線に合流させる
git branch -d add-wiki     # 用済みの枝を消す
```

図にすると、こういう形です。mainから枝分かれし、作業を重ね、最後に合流します。

```
        A---B  add-wiki
       /      \
  X---Y--------M  main
```

枝の名前は、目的がわかるものにします。`fix-form-validation`、`add-npo-article` のように、何をする枝かが読めれば十分です。

いま自分がどの枝にいるかは、常に意識してください。ブランチを切ったつもりで本線を編集していた、というのはよくある失敗です。`git status` の1行目に現在のブランチ名が出るので、作業を始める前に確認する習慣をつけると防げます。

注意点を1つ。枝を長く放置すると、本線がどんどん進んで差が開き、合流時のぶつかり合い（コンフリクト）が大きくなります。枝は短く、こまめに合流させる。これが実務での鉄則です。
