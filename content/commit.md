## ひとことで

変更をひとかたまりにして、説明文を付けて履歴に刻む操作です。Gitのセーブポイントにあたります。

## なぜ大事?

コミットは、Gitの履歴を作る最小単位です。あとで「いつ壊れたのか」を調べるとき、「どこまで戻せば安全か」を決めるとき、手がかりになるのはコミットの粒度と説明文だけです。

半年後に自分の書いたコードを見て、なぜこう直したのか思い出せる人はいません。思い出させてくれるのがコミットメッセージです。ここを雑に書くと、履歴はあるのに読めない、という状態になります。

AIかけこみ寺の共同開発ルールでも、「1コミット1目的」を原則にしています。複数人が別のパソコンから同じサイトを触る以上、他人がその変更を1行の説明で理解できるかどうかが、そのまま作業の速さになります。

## やさしい解説

コミットは、日記の1ページだと思ってください。

1ページに1日ぶんの出来事を書くから、あとから読み返せます。3か月ぶんを1ページに詰め込んだら、書いた本人にも読めません。逆に、1文字書くたびにページを変えるのも読みにくい。ちょうどいい区切りは、「1つの用事が終わったところ」です。

実際の手順は2段階です。まず記録したいファイルを選んで台に載せ（ステージング）、次に確定します。

```bash
git add content/npo.md          # 記録するファイルを選ぶ
git commit -m "NPO法人の記事を追加"  # 説明を付けて確定する
```

なぜ2段階なのか。ファイルを5つ直したけれど、今回記録したいのは2つだけ、ということがあるからです。選んでから確定できるので、目的ごとにきれいに履歴を分けられます。

コミットメッセージの書き方には、公式ドキュメントにも推奨があります。1行目は50文字程度までの短い要約にし、詳しく書きたいときは1行あけてから本文を続ける、という形です。

良い例と悪い例を並べます。

悪い例：

```
修正
いろいろ
aaa
```

良い例：

```
講座申込フォームの必須チェックが効かない不具合を修正

メールアドレス欄が空でも送信できていた。
入力チェックの条件式が逆になっていたため修正。
```

悪い例は、履歴に残っていても何の役にも立ちません。良い例は、半年後の他人（そして自分）を救います。

コミットには、変更内容のほかに、作った人の名前、日時、そして1つ前のコミットへの参照が入ります。この参照がつながって、鎖のような履歴ができあがります。だから、途中の1つを抜き差しすると鎖全体が変わる。これがGitの改ざんの検知しやすさにつながっています。

注意点を1つ。コミットしただけでは、まだ自分のパソコンの中だけの記録です。他の人に届けるにはプッシュが必要です。コミットで安心して、共有し忘れる。初心者がいちばんよくやるつまずきです。
