## ひとことで

サーバー側のリポジトリの最新の変更を、自分の手元に取り込む操作です。

## なぜ大事?

共同作業の事故の多くは、古い状態のまま作業を始めたことが原因です。他の人が昨日直した部分を知らずに、自分も同じ場所を直す。合流のときに必ずぶつかります。

プルは、この事故を防ぐための最初の一手です。作業を始める前にプルする、という習慣だけで、衝突の量ははっきり減ります。

AIかけこみ寺の共同開発ルールでも、作業前に最新を取り込むことを第1条にしています。複数人が別々のパソコンから同じサイトを触っているので、自分の手元の見た目を信じないこと。サーバー側が正である、という前提を毎回確かめる操作がプルです。

## やさしい解説

プルは、グループ作業の途中で「いまの最新版ちょうだい」と全員に確認する行為です。

3人で1つの資料を作っているとします。あなたが2日ぶりに作業を再開するとき、いきなり自分の手元のファイルを開いて書き始めたら、その2日間の他の人の仕事は反映されていません。まず最新版をもらってから続きを書く。当たり前の話ですが、Gitでは明示的にこの操作をします。

操作は1行です。

```bash
git pull
```

公式ドキュメントによれば、この1行は実は2つの動作を続けて行っています。

1. フェッチ：サーバーから新しい変更をダウンロードする
2. 統合：それを自分の現在のブランチに合流させる

つまり `git pull` は、`git fetch` と `git merge` をまとめたものです。分けて実行することもでき、慣れてくるとそのほうが安全な場面もあります。まずフェッチして中身を確認し、問題なさそうなら合流する、という進め方です。

```bash
git fetch                  # 取ってくるだけ。手元のファイルはまだ変わらない
git diff origin/main       # 何がちがうか確認する
git merge origin/main      # 納得してから合流する
```

統合のしかたは選べます。マージだと合流の記録（マージコミット）が残り、履歴が枝分かれした形になります。リベース（`git pull --rebase`）だと、自分の作業を相手の変更の上に載せ直すので、履歴が1本にそろって読みやすくなります。AIかけこみ寺では `git pull --rebase` を使う運用です。

注意点を2つ。第1に、リベースは履歴を作り直す操作なので、すでに共有した（プッシュ済みの）コミットに対して使うと、他の人の履歴とずれます。まだ公開していない自分の作業にだけ使ってください。第2に、プルの途中でコンフリクトが出たら、そこで止まります。慌てずに、ぶつかった箇所を直して続けるか、いったん中止して相談すること。無理に押し切ると、他人の作業を消す方向に進みがちです。
