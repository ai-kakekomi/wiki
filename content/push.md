## ひとことで

自分のパソコンに溜めたコミットを、サーバー側のリポジトリへ送る操作です。

## なぜ大事?

Gitでは、コミットしただけでは誰にも届きません。手元のノートに書いただけの状態です。プッシュして、はじめて他の人が見られる場所に載ります。

これは不便に見えて、実はよくできた設計です。試行錯誤の途中経過は手元だけに置いておき、人に見せられる形になってから共有できるからです。ネットのない場所でも作業を続けられるのも、この分離のおかげです。

AIかけこみ寺の共同開発ルールでは、プッシュの直前にもう一度サーバー側の最新を取得し、自分の差分を確かめてから送る、と決めています。他の人が先に何かを入れているかもしれないからです。ローカルの見た目ではなく、サーバー側が正である、という原則がここにあります。

## やさしい解説

プッシュは、手元で書いた原稿を、みんなが見る掲示板に貼りに行く動作です。

書いている途中の紙は机の上にあります。清書して、日付を書いて、それから掲示板に貼る。貼った瞬間から、他の人はそれを読み、その上に自分の紙を重ねていきます。だから、貼る前に掲示板の現状を見るのが礼儀になります。

基本の操作はこうです。

```bash
git push origin main
```

`origin` が送り先の名前（クローンしたときに自動で登録されます）、`main` が送るブランチ名です。初めてそのブランチを送るときは、対応関係を覚えさせておくと次から楽になります。

```bash
git push -u origin add-wiki-articles
```

以後は `git push` だけで済みます。

覚えておくべき安全装置が1つあります。Gitは既定で、早送りできる場合だけプッシュを許します。つまり、サーバー側にあなたが持っていない変更があると、プッシュは拒否されます。これは意地悪ではなく、他人の作業を上書きさせないための防御です。拒否されたときの正しい対応は、まずプルして相手の変更を取り込み、必要なら合流させてから、もう一度プッシュすることです。

ここで絶対にやってはいけないのが、面倒だからと `--force`（強制プッシュ）を使うことです。これはサーバー側の履歴を自分のもので置き換える操作で、他人のコミットを丸ごと消し飛ばします。どうしても必要な場面はありますが、そのときも `--force-with-lease` のように、相手の状態を確認したうえで上書きする安全な形を使います。

実務のコツを3つ。第1に、こまめにプッシュすること。溜めるほど衝突が大きくなります。第2に、プッシュ前に自分の差分を確認すること。第3に、大きめの変更を送ったら、チームに一言伝えること。「無言で本番が変わっていた」を減らすだけで、共同作業の摩擦はかなり下がります。
