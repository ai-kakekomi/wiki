ひとことで

枝分かれしていた作業を、1本にまとめ直す操作です。

なぜ大事?

ブランチを作れることに意味があるのは、あとで合流できるからです。合流できなければ、ただ作業がバラバラになるだけです。マージは、分けた作業を成果として回収する工程にあたります。

そして共同作業でいちばん怖い場面が、まさにここです。2人が同じ場所を別々に直していたとき、どちらを残すのか。Gitはこれを勝手に決めず、人間に判断させます。黙って片方を消さない。この設計のおかげで、作業が行方不明にならずに済んでいます。

AIかけこみ寺のように、複数のメンバーが別々のパソコンから同じサイトを触る運用では、マージの扱いに慣れているかどうかが、そのまま事故率になります。

やさしい解説

マージは、共同で書いたレポートの原稿を1本にまとめる作業に似ています。

Aさんが第1章を、Bさんが第2章を書いてきたなら、まとめるのは単純です。触った場所がちがうからです。困るのは、2人とも第1章の同じ段落を書き直してきたときです。どちらを採るか、あるいは混ぜるかは、内容を読める人にしか決められません。

Gitのマージにも、この2つのパターンがあります。

すんなり終わる場合。 変更箇所が重なっていなければ、Gitが自動で1つにまとめ、マージコミットという合流の記録を作ります。また、本線がまったく進んでいない場合は、単に印を進めるだけで済みます（早送りマージ、fast-forwardと呼びます）。

ぶつかる場合。 同じファイルの同じ行が両方で変わっていると、コンフリクト（衝突）になります。このときGitは作業を止めて、ファイルの中にこういう印を書き込みます。

<<<<<<< HEAD
参加費は無料です。
=======
参加費は無料（教材費のみ実費）です。
>>>>>>> add-fee-note

上が自分の側、下が取り込もうとしている側です。人間がこの部分を正しい1つの文に書き直し、印の行を消して、次のように進めます。

git add 対象ファイル
git merge --continue

途中でやめたいときは git merge --abort で、マージ前の状態に戻せます。これを知っているだけで、コンフリクトの怖さはかなり減ります。手が止まったら元に戻せるからです。

コツは3つあります。第1に、マージする前に本線の最新を取り込んでおくこと。第2に、枝を長生きさせないこと。1週間分の差分より、1日分の差分のほうが確実に衝突が小さくなります。第3に、コンフリクトが起きたら、相手が何をしようとしていたかを確認してから決めること。自分の側を機械的に採用するのは、他人の作業を消すのと同じです。

注意点を1つ。マージが完了しても、それは自分の手元の話です。共有するにはプッシュが必要です。また、GitHubを使う場合は、マージの前に内容を確認しあう仕組みとしてプルリクエストを挟むのが一般的です。
